# Способности сыщика — спец-действие и пассив

> Механика готова, данные пустые. Способности дописываются руками в
> `data/investigators.json`. Сыщик без полей `ability`/`passive` работает как раньше.

## Решения

- Хранение — **`data/investigators.json`** (не CMS): сыщики нужны уже в лобби, до подключения к партии.
- Спец-действие — **тратит 1 из 2 действий, один раз за раунд**.
- Доступно — **только в фазе действий** (как Отдых/Ресурс).
- Пассив — **постоянный модификатор проверок**, без тапа.

## Форма данных

Оба поля необязательные, кладутся в карточку сыщика:

```json
{
  "name": "Ezra Gilman",
  "skills": { "will": 3, "lore": 1 },

  "ability": {
    "name": "INV_EZRA_ABILITY_NAME",
    "text": "INV_EZRA_ABILITY_TEXT",
    "do": [ { "do": "gainClue", "count": 1 } ]
  },

  "passive": {
    "name": "INV_EZRA_PASSIVE_NAME",
    "text": "INV_EZRA_PASSIVE_TEXT",
    "mods": [ { "do": "addToDie", "amount": 1, "context": "combat" } ]
  }
}
```

`name`/`text` — ключи из `translations.csv` (не сырой текст: иначе не переведётся).
`ability.name` идёт подписью на кнопку.

## Спец-действие (`ability.do`)

Обычная программа Effect-DSL — те же глаголы, что в встречах и картах Мифов:
`gainClue`, `healSanity`, `healHealth`, `gainResource`, `gainAsset`, `gainSpell`,
`move`, `closeGate`, `spawnMonster`, `placeClue`, `retreatDoom` и т.д.

Мутации сыщика применяются сразу, board-эффекты уходят в общий обработчик,
изменения попадают в ленту исходов («+1 улика»), над фишкой всплывает облачко.

**Ограничение:** программа исполняется **мгновенно**. Узел `test` (видимая проверка
с броском) пока НЕ поддержан — для него нужен интерактивный цикл, как у действий
состояний (`condition_action`). Если способность просится с проверкой — скажи,
это отдельный кусок работы.

### Встроенные виды (`ability.kind`)

Когда действие **требует ввода игрока**, программой оно не выражается — тогда
вместо `do` ставится `kind`, а поведение живёт в коде (`phase_controller`).

| kind | Что делает | Кто |
|---|---|---|
| `convertVitality` | «Потратьте любое число здоровья или рассудка и восстановите столько же другого» — игрок выбирает направление и величину | Мэй Линь |

```json
"ability": { "name": "INV_MEI_LIN_ABILITY_NAME", "text": "…", "kind": "convertVitality" }
```

Гварды `convertVitality`: источник **не опускается ниже 1** (иначе способность
открывала бы себе Порог), приёмник не переливается выше максимума. Величина
клампится под оба предела; если переливать нечего — действие не тратится.

Новый вид = новая ветка в `_run_investigator_ability` + (если нужен ввод) модалка
в `action_panel`. Это код, а не данные — но виды переиспользуются между сыщиками.

## Пассив (`passive.mods`)

Массив узлов, которые подмешиваются в **любую** проверку сыщика автоматически.
Поддержаны только check-mod-глаголы:

| Глагол | Что делает |
|---|---|
| `rerollDice` | бесплатный переброс |
| `rerollMatching` | переброс совпадающих |
| `enhanceReroll` | усиление переброса |
| `rollAdditionalDice` | +кубы в пул |
| `addToDie` | +N к кубу |
| `convertDie` | замена грани |
| `improveSkill` / `impairSkill` | ±N к навыку |
| `minDice` | минимальная грань |
| `substituteSkill` | проверка другим навыком |

Прочие глаголы в `mods` **молча игнорируются** — это не данные, а новый слой правил.

### Фильтр по контексту

`context` ограничивает, где пассив работает. Без поля (или `"anyTest"`) — везде,
включая Порог (спас-бросок).

```json
{ "do": "rerollDice", "count": 1, "context": "combat" }
```

Контексты берутся из тех же значений, что у активов: `combat`, `encounter`,
`acquireAssets`, `anyTest` и т.п.

### Триггерные пассивы (`passive.triggers`)

Пассив, который срабатывает не на проверке, а на **игровом событии**:

```json
"passive": { "name": "…", "text": "…", "triggers": [ { "on": "improveSkill", "repeat": 1 } ] }
```

| `on` | Что делает | Кто |
|---|---|---|
| `improveSkill` | улучшение навыка применяется ещё `repeat` раз | Мэй Линь |

Только на **улучшение** — ухудшение (`impairSkill`) не удваивается, иначе пассив
работал бы против владельца. Потолок `SKILL_MOD_CAP` (±2) всё равно клампит итог.

## Где это в коде

| Слой | Файл |
|---|---|
| Чтение данных | `scripts/core/data/investigators.gd` — `ability`/`passive`/`passive_check_mods` |
| Пассив в проверке | `scripts/core/game/check_flow.gd` — сидируется в `make_check` (единая точка **всех** проверок) |
| Исполнение действия | `scripts/core/game/phase_controller.gd` — `_run_investigator_ability` |
| Гейт для UI | `scripts/core/game/game_state.gd` — `can_use_ability` / `my_ability` |
| Кнопка | `scripts/ui/action_panel.gd` — видна только при наличии способности |
| Лента | `data/action_log.json` → id `investigator_ability` |

Тесты: `test/unit/test_investigator_abilities.gd` (10 шт.) — контракт фильтров и
сидирования; данные подменяются фикстурой, реальные сыщики не задействованы.

## Что осталось на будущее

- **Проверка внутри спец-действия** (`test`) — нужен интерактивный цикл + драйвер
  `pending_check`, по образцу `condition_action`.
- **Пассивы вне проверок** — «−1 урона от монстров», «двигается на 2 локации»:
  требуют новых правил, а не данных.
- **Свой медальон** в ряду действий — сейчас текстовая кнопка (арта нет).
- **Показ пассива игроку** — сейчас нигде не отображается; напрашивается строка
  в панели сыщика или на карточке выбора.
