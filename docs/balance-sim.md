# Симулятор баланса карт (`card_sim.gd`)

> Headless Monte-Carlo прогон карт на **реальной** математике движка. Считает
> вероятности успеха/победы по сетке навыков, монстров и перебросов; помечает
> выбросы; пишет HTML + JSON отчёт. Один источник правды с игрой — цифры не
> расходятся.

Дополняет [check-pipeline.md](check-pipeline.md): тот описывает **как** проверка
устроена в игре, этот — как её **прогнать тысячами бросков** для оценки баланса.

---

## 1. Зачем так

Карт будет много, и вопрос не «работает ли механика» (это ловит
`test_data_integrity`, см. §7), а **как карта играется**: не слишком ли слаба, не
имба ли, как её вытягивают перебросы. Ручной прикидки на бумаге не хватает —
нужен статистический прогон против настоящих монстров.

Ключевое решение — **не писать параллельную модель кубов**. Симулятор дёргает те
же самые `Dice` / `AssetCatalog` / `MonsterCatalog` / `SpellCatalog`, что и живая
игра. Значит:

- цифры отчёта = цифры реального боя (нет дрейфа «симулятор посчитал одно, игра
  делает другое»);
- поправил математику в `Dice` — отчёт автоматически поехал следом;
- фикс-сид (`seed(12345)`) → отчёт **воспроизводим** и диффабелен (можно коммитить
  и видеть, что сдвинулось после ребаланса).

`card_sim.gd` — `extends SceneTree`, самостоятельная точка входа (не автозагрузка,
не часть игры). Запускается headless и сразу `quit()`.

---

## 2. Как запустить

```powershell
./run_sim.ps1
# или напрямую:
godot --headless --path . -s res://tools/card_sim.gd
```

`run_sim.ps1` берёт Godot из `$env:GODOT`, иначе из `godot` в PATH.

**Отчёт:** `<проект>/sim-report/balance.html` + `balance.json` (папка в `.gitignore`).
В консоль дублируется краткая сводка. HTML — тёмная таблица, ячейки вероятностей
покрашены по градиенту (красный <15% → оранжевый → жёлтый → зелёный ≥65%),
колонка «флаг» подсвечивает выбросы.

---

## 3. Что покрыто (вертикальный срез)

Симулятор гоняет **явно вписанные** карты по сетке параметров — не весь каталог
(см. §6 про масштабирование). Сейчас в срезе:

| Категория   | Карты                        | Что меряется                                    |
|-------------|------------------------------|-------------------------------------------------|
| Оружие (бой)| `45_automatic`, `18_derringer` | P(победа над монстром), ~урон по сыщику          |
| Заклинание  | `banishment`                 | P(каст) и P(победа) — Lore-каст с `maxToughness` |

Сетка (константы вверху файла):

```gdscript
const ITERS    := 20000                   # бросков на ячейку
const STRENGTHS := [2, 3, 4]              # профили сыщика по Силе (оружие)
const LORES    := [2, 3, 4]               # профили по Знанию (заклинания)
const MONSTERS := ["zombie", "deep_one", "gug"]  # растущая стойкость 2/2/4
const REROLLS  := [0, 1, 2]               # доступно перебросов (фокус/улики)
```

Итог на ячейку — тройка вероятностей по числу перебросов (0/1/2), чтобы видеть не
только «голую» карту, но и сколько её вытягивает ресурс перебросов.

## 4. Модель проверки (что симулятор считает и чего НЕ считает)

Ядро — `_roll(base_skill, external_mod, mods, skill, target, rerolls)`. Оно
воспроизводит `CheckFlow`, но только **бросковую** часть:

```
пул   = max(1, навык + внешний_мод + Dice.pre_roll_bonus(mods, skill))
base  = Dice.roll(пул)
успехи= count_successes_with(apply_add_to_die(base, mods, skill), mods, skill)
пока успехи < target и есть перебросы:
    рероллим ПЕРВЫЙ провальный куб (<5) → Dice.roll_one()
    пересчитываем успехи (addToDie идемпотентно заново)
```

Что берётся из **реальных** каталогов:

- `AssetCatalog.passive_check_mods(asset, "combatEncounter")` — пассивы оружия
  (`improveSkill` у автомата, `addToDie` у деринджера) идут в тот же конвейер
  `Dice`, что в игре.
- `MonsterCatalog.by_id` → `combat.modifier` (мод пула), `toughness` (порог),
  `combat.damage` (урон по сыщику), `apply_resistance` (физ/маг резист).
- `SpellCatalog.by_id("banishment")` → `front.modifier` (−1), правило reach =
  успехи+1 (изгнать монстра стойкости T нужно успехов ≥ T−1).

**Осознанные упрощения** (о них честно сказано в шапке HTML):

| Упрощение | Что это значит |
|-----------|----------------|
| Перебрасывается **первый** провальный куб, не «самый близкий к успеху» | стратегия игрока может быть чуть лучше → реальные P слегка выше оценки |
| Перебросы стремятся к `target` успехов, дальше не тратятся | нет добора «в запас» |
| Только `improveSkill`/`addToDie`/`convertDie`/`rollAdditionalDice` из модов | эффекты вне броскового конвейера (`triggered`, `whileHeld`, спавн врат, перемещение) **игнорируются** — см. §7 |
| Оружие: одна атака, `damage = combat.damage − успехи` | без многораундового размена, без условий монстра |
| Заклинание: `p_cast` = прошёл (≥1 успех), `p_win` = успехов ≥ стойк−1 | без побочек провала каста |

То есть модель точна для **пуловых/бросковых** карт (оружие, боевые заклинания) и
**неприменима** к картам, которые делают что-то помимо изменения броска.

## 5. Флаги выбросов

`_flag(p_min_rerolls, p_max_rerolls)` — эвристика «проверь тюнинг», крайности:

- **`слабо`** — даже с максимумом перебросов P(успех) < 15%. Карта почти не
  срабатывает при любых ресурсах.
- **`имба`** — без единого переброса P(успех) > 85%. Карта проходит тривиально.
- пусто — в рабочем диапазоне.

Пороги (`0.15` / `0.85`) — вкусовые, правятся в `_flag`. Это не «баг», а маркер,
куда посмотреть глазами.

---

## 6. Как масштабировать

Механика (пул / успехи / перебросы / резист / стойкость) уже **общая и точная** —
расширение = добавить карты и параметры, не трогая ядро.

- **Ещё оружие** — впиши id в список в `_sim_weapons` (`["45_automatic", …]`).
- **Ещё заклинания** — по образцу `_sim_banishment` (навык, `modifier`, правило
  победы из его `do`).
- **Автообход каталога** (следующий шаг, ещё не сделан) — вместо хардкода
  пройтись по `AssetCatalog`/`SpellCatalog`, отфильтровать карты с бросковыми
  модами и прогнать каждую. Тогда срез станет полным по этой категории. Карты вне
  бросковой модели при этом надо **явно пропускать** (и логировать пропуск, чтобы
  «не покрыто» не читалось как «покрыто и ок»).

## 7. Границы: симулятор ≠ детектор неподдержанных механик

Важно не перепутать два «выявления»:

| Вопрос | Кто отвечает |
|--------|--------------|
| Есть ли у нас механика (verb) под карту? | `test_data_integrity.gd` — сверяет **все** `do:` каталога с `effect-manifest.json` |
| Ссылки состояний/стартовых наборов валидны? | `test_data_integrity.gd` |
| Карта сбалансирована по цифрам? | **этот симулятор** (только вписанные карты) |
| Verb реально исполняется, а не заглушка? | пока **никто автоматически** (кандидат на coverage-тест `effect_runner`) |

Симулятор карту с неподдержанной механикой **не пометит** — он её просто не учтёт
(возьмёт бросковые моды, остальное молча пропустит). Ловля «неподдержанных
механик по объявлению» — задача `test_data_integrity`, а не отчёта баланса.

## 8. Карта файлов

| Файл | Роль |
|------|------|
| `tools/card_sim.gd` | сам симулятор (`_roll` ядро, `_sim_weapons`/`_sim_banishment`, отчёты) |
| `run_sim.ps1` | лаунчер (headless Godot) |
| `sim-report/balance.{html,json}` | выход (gitignored, воспроизводим по фикс-сиду) |
| `scripts/core/game/dice.gd` | математика кубов, которую симулятор переиспользует |
| `scripts/core/data/{asset,monster,spell}_catalog.gd` | источники данных карт/монстров |
| `test/unit/test_data_integrity.gd` | детектор неподдержанных verb'ов (см. §7) |
